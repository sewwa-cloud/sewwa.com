# 7 Hreflang Mistakes That Make Google Ignore Your Translations

You translated the site. You shipped `/de/`, `/fr/`, and `/es/`. You even added hreflang tags, ticked the box, and moved on. Then Search Console shows your German page outranked by the English one in Germany, and nobody can tell you why.

Here's the uncomfortable part: hreflang fails silently. There's no build error, no console warning, and Google no longer gives you a dedicated report that lists hreflang problems. When the annotations are wrong, Google doesn't complain. It just ignores them and picks a version on its own.

This list covers the seven hreflang mistakes we see most often on modern JavaScript stacks, ranked by how much damage they do and how often they show up. For each one you'll get the rule, why it breaks, and a fix you can paste into a Next.js App Router project. We lean on Google's own documentation for the rules, because most hreflang advice online is a game of telephone.

One more thing before we start. Hreflang is a routing hint for classic search results. It isn't a ranking boost, and as we'll see in mistake #7, it matters less in AI-generated answers. So think of it as plumbing: invisible when it works, expensive when it leaks.

## 1. Missing Return Links (The Classic)

Google's rule is blunt: if two pages don't both point to each other, the tags will be ignored. Every language version has to list itself *and* every other version. That's a full mesh, not a one-way street.

This breaks constantly in headless setups. The English page knows about the German one because the CMS has a translation field, but the German page was published through a different template that never learned about English. Result: Google sees `en → de` but no `de → en`, and discards the pair.

**SEO impact:** the wrong language version ranks in the wrong country, and your translated pages get treated as duplicates competing with the original.

**Fix:** generate the alternates from one shared source of truth, never per page by hand.

```ts
// lib/i18n.ts
export const locales = ["en", "de", "fr"] as const;
export const base = "https://www.example.com";

export function buildAlternates(path: string, available: readonly string[]) {
  const languages: Record<string, string> = {};
  for (const l of available) languages[l] = `${base}/${l}${path}`;
  languages["x-default"] = `${base}/en${path}`;
  return languages;
}
```

Every page template calls the same function. If a locale exists for one page, it exists in every page's alternates, which is what makes the mesh symmetrical.

## 2. Invalid Language and Region Codes

This one is almost funny, except it isn't. Google's docs spell it out: the language code is ISO 639-1, optionally followed by an ISO 3166-1 Alpha-2 region. A country code on its own is invalid. Codes like `es-419` are unsupported, and reserved values such as `EU`, `UN`, or `UK` have no effect.

The greatest hits: `en-UK` (the region code for the United Kingdom is `GB`), `uk` used to mean "United Kingdom" (it's Ukrainian), `tw` instead of `zh-TW`, and `be` for Belgium (it's Belarusian). Script codes like `zh-Hans` and `zh-Hant` are fine.

**SEO impact:** an invalid code means that annotation is dropped, and your return-link mesh from mistake #1 now has a hole in it.

**Fix:** treat codes as a typed enum, not free text.

```ts
const VALID = new Set(["en", "en-GB", "en-US", "de", "de-AT", "fr", "fr-CA", "zh-Hans", "zh-Hant"]);
export function assertLocale(code: string) {
  if (!VALID.has(code)) throw new Error(`Invalid hreflang code: ${code}`);
}
```

Fail the build on a bad code. A thrown error at compile time is much cheaper than three months of wrong-country rankings. ## 3. Hreflang Pointing at URLs That Redirect, 404, or Aren't Canonical

Hreflang URLs should be the final, indexable, canonical address of each version. In practice they often aren't. Typical offenders: a trailing-slash mismatch that triggers a 308, a `www` vs non-`www` slip, or a canonical tag on `/de/page` that points somewhere else entirely.

When the canonical says "the real page is X" and hreflang says "the German page is Y," you've handed Google two contradictory instructions. Google picks one, and it's not always the one you wanted.

**SEO impact:** annotations get dropped, and the wrong URL ends up indexed.

**Fix:** make canonical and hreflang read from the same function, and make each page self-canonical.

```ts
// app/[locale]/blog/[slug]/page.tsx
export async function generateMetadata({ params }) {
  const { locale, slug } = await params;
  const available = await getAvailableLocales(slug); // only real translations
  const url = `${base}/${locale}/blog/${slug}`;
  return {
    alternates: {
      canonical: url,
      languages: buildAlternates(`/blog/${slug}`, available),
    },
  };
}
```

Then validate it. Fetch every alternate URL, assert a 200 with no redirect, and assert the canonical equals the URL you fetched. ## 4. Misusing x-default

Google describes `x-default` as the fallback for when no listed language matches the visitor. It suits a language selector page or an auto-redirecting home page. No language code needed.

The mistakes are predictable. Teams omit it entirely, point it at a URL that itself redirects (so it can't link back into the cluster), or assume it's a "default language" tag that must match one of the locales. It doesn't have to. A global landing page or a selector is a perfectly good x-default.

Another trap in the App Router: some tutorials put `x-default` in one place for page metadata and leave it out of the sitemap generator. The two methods then disagree, which leads straight into mistake #6.

**SEO impact:** users from unmatched regions land on an arbitrary version, and some validators flag the whole cluster.

**Fix:** one `x-default`, pointing at a stable, non-redirecting 200 URL, emitted by the same helper as everything else (see the `buildAlternates` function above).

## 5. Auto-Redirecting by IP or Accept-Language

This is the mistake that feels like good UX. A visitor from Berlin hits the English home page, and your middleware helpfully sends them to `/de/`. Lovely for humans. Terrible for crawlers.

Google's documentation explains why. Googlebot's default IP addresses appear to be based in the USA, and its requests don't set `Accept-Language`. So if you serve different content from one URL based on perceived location or language, Googlebot mostly sees the US/English variant and may never crawl the rest. Google's own recommendation is to use separate locale URLs with hreflang annotations, and to link to other versions so users can choose rather than redirecting them by guess.

**SEO impact:** whole locale trees never get crawled or indexed, and the symptom looks like "Google just doesn't like our German pages."

**Fix:** keep every locale on its own URL, and use a dismissible banner instead of a forced redirect.

```ts
// middleware.ts — suggest, don't force
export function middleware(req: NextRequest) {
  const res = NextResponse.next();
  const pref = req.headers.get("accept-language")?.slice(0, 2);
  if (pref && pref !== currentLocale(req)) {
    res.headers.set("x-suggest-locale", pref); // UI shows a banner
  }
  return res;
}
```

Edge logic deserves extra care here, since region-based behavior can look like cloaking if you treat Googlebot differently from users. ## 6. Alternates That Point to Pages That Don't Exist (or Disagree Across Methods)

This one is native to dynamic frameworks. Your `generateMetadata` loops over *all* supported locales and prints an alternate for each, even when a given article was never translated into French. The tag points at a 404, or at a redirect to the English page.

Related: some sites emit hreflang in the `<head>` and also in the XML sitemap, and the two lists drift apart. Google treats the three methods (HTML link tags, HTTP headers, sitemap `xhtml:link`) as equivalent and says using more than one adds no benefit. So pick one. Two sources of truth means two chances to be wrong.

A smaller cousin: sitemap `lastmod` set to `new Date()` on every build. If every URL claims to have changed just now, the signal is worthless.

**SEO impact:** broken or conflicting annotations get ignored, and crawl budget gets wasted on dead alternates.

**Fix:** only list locales that have a real, published translation (the `getAvailableLocales` call in mistake #3), and choose a single method. For large sites the sitemap is usually easier to audit centrally:

```ts
// app/sitemap.ts
export default async function sitemap() {
  const posts = await getAllPosts();
  return posts.flatMap((p) =>
    p.locales.map((l) => ({
      url: `${base}/${l}/blog/${p.slug}`,
      lastModified: p.updatedAt, // real content date
      alternates: { languages: buildAlternates(`/blog/${p.slug}`, p.locales) },
    }))
  );
}
```

If your translated pages are statically regenerated, make sure the alternates update on the same clock as the content, otherwise you ship a stale mesh. ## 7. Treating Translation as the Whole Job

Here's the 2026 twist. Hreflang tells traditional search which URL to show. It does not tell an AI system anything useful about which version to *use*.

Search Engine Land's recent analysis of international SEO argues visibility is increasingly "a selection problem, not a ranking problem." AI systems convert content into semantic representations, so pages with substantively the same information in different languages can be treated as interchangeable, and the most confident global version may be reused across markets, even when it's wrong for a local user. Their suggestion: real market differences (legal disclosures, pricing, availability, shipping and compliance rules) rather than translation alone. Treat that as one expert's analysis rather than a measured law, since the piece itself offers no citation data.

Vendor content makes similar claims, such as that non-English AI answers lean on English sources, but those pieces also offer no numbers, so we'd hold them loosely. What's safe to say: Google's own docs note localized versions count as duplicates when the main content stays untranslated, and thin machine translation gives nobody a reason to prefer your localized page.

**SEO impact:** pages that are only translated, not localized, risk being collapsed into the original in both classic and AI results.

**Fix:** localize what actually differs by market (prices, currency, legal copy, local examples, support details), keep naming and URLs consistent, and tie your markets together with entity signals. Our guide on [Organization Schema in 2026: How to Actually Earn a Knowledge Panel](/organization-schema-knowledge-panel-entity-seo-2026/) covers the `sameAs` and entity groundwork that helps here. Fewer, stronger market pages beat a hundred shallow translations.

## Honorable Mentions

**Relative URLs.** Alternate URLs must be fully qualified, with protocol and domain. `/de/page` won't do.

**Hreflang in the `<body>`.** Annotations belong in the `<head>`, HTTP headers, or the sitemap. Links dropped into the body are ignored.

## How to Audit Your Own Site in 20 Minutes

You don't need a paid crawler to get a first answer. Here's a minimal return-link checker you can run locally or in CI:

```js
// check-hreflang.mjs
import { parse } from "node-html-parser";

async function alternates(url) {
  const html = await (await fetch(url, { redirect: "manual" })).text();
  return parse(html).querySelectorAll('link[rel="alternate"][hreflang]')
    .map((n) => [n.getAttribute("hreflang"), n.getAttribute("href")]);
}

const start = process.argv[2];
const first = await alternates(start);
for (const [lang, href] of first) {
  const back = await alternates(href);
  if (!back.some(([, h]) => h === start)) console.error(`NO RETURN LINK: ${lang} ${href}`);
}
```

Run it against your top 50 URLs by organic traffic. If it prints a single `NO RETURN LINK`, you've found a mistake #1 in the wild. Then check your server logs to see whether Googlebot is even reaching the locale URLs; [9 Things Your Server Logs Reveal That Search Console Can't](/server-log-analysis-seo-2026-what-search-console-misses/) shows how. And if you verify crawler identity at the edge, [7 Steps to Implement Web Bot Auth and Verify Googlebot in 2026](/web-bot-auth-implementation-verify-googlebot-2026/) pairs well with this, because Google recommends verifying Googlebot by reverse DNS rather than trusting the user agent.

## Conclusion

Hreflang looks like seven lines of HTML, which is exactly why it gets neglected. But the failure modes are structural: missing return links, bad codes, canonical conflicts, a sloppy `x-default`, redirects keyed on location, alternates for pages that don't exist, and translations with nothing local about them.

The common thread is a single source of truth. Generate canonical, hreflang, and sitemap entries from one function, restrict them to real translated pages, keep every locale on its own URL, and test the mesh in CI. Do that, and your international SEO stops depending on luck.

If you only fix one thing this week, fix #5. A forced redirect can hide an entire language from Google, and nothing else on this list is that quiet.

## FAQ

### Does hreflang improve rankings?
No. It's a routing hint that helps Google show the right language or regional version. It doesn't boost a page's ranking strength.

### Should I use the head, HTTP headers, or the sitemap?
Google treats them as equivalent and says using more than one adds no benefit. Pick one and keep it consistent. HTTP headers suit non-HTML files like PDFs; the sitemap is easiest to audit at scale.

### Is x-default required?
No, but it's recommended as a fallback for visitors whose language isn't listed, such as a language selector or an auto-redirecting home page.

### Does Google use the HTML lang attribute to detect language?
No. Google's documentation says it uses algorithms based on visible content, not hreflang or the `lang` attribute, to determine a page's language.
